# Rally V1 Implementation Plan

> **For agentic workers:** Use the native execution workflow and implement this plan task by task. Keep each deliverable reviewable and commit only validated work.

**Goal:** Build Rally as a secure multi-user progress app with persistent Supabase data, responsive dashboard and history, automated checks, and a verified release when external access is available.

**Architecture:** Next.js App Router renders protected pages on the server and submits Zod-validated server actions through Supabase's cookie-based SSR client. PostgreSQL migrations own workspace permissions, local-day check-ins, invitations, and integrity constraints. Small date/streak utilities and accessible shared components keep business rules and UI reusable.

**Tech Stack:** Next.js App Router, React, strict TypeScript, Tailwind CSS, Supabase PostgreSQL/Auth and `@supabase/ssr`, Zod, Vitest, Playwright, GitHub Actions, Vercel.

**Spec:** `docs/design/rally-v1.md`, derived from the Rally master build prompt.

## Global Constraints

- Use one public GitHub repository named `rally` if available and `main` only; never overwrite an existing repository, force-push, or create PRs.
- Use current stable patched compatible dependency versions and commit the lockfile.
- Keep secrets out of Git and browser code; commit `.env.example` with placeholder variable names only.
- Apply RLS to every exposed application table and use server-side validation and authorization for every mutation.
- Do not hardcode a 60-day challenge limit, fake data, placeholder production functionality, or dead controls.
- Preserve historical challenge and progress records; use server-trusted timestamps and challenge-local calendar dates.
- Maintain strict TypeScript, accessible responsive UI, original SVG branding, and no disabled lint/type checks.
- Do not claim CI, account authorization, database security, screenshots, or deployment results that were not observed.

## Review Focus

- A second concurrent invite redemption cannot exceed `max_uses` or create duplicate memberships; test the transaction under simultaneous requests.
- DST spring-forward and fall-back days still map one check-in to one challenge-local calendar date; test IANA-zone boundaries.
- A member cannot reach another workspace's record by guessing UUIDs or submitting another user's owner ID; test negative RLS and server-action cases.
- Whitespace-only and oversized text is rejected without storing partial content; test each public mutation schema.
- Auth callback and return paths cannot redirect outside Rally; test encoded and absolute URL variants.

## Execution Notes

This is a single integrated V1 plan because auth, workspace isolation, challenge-local dates and activity views share one permission and data model. The independent deliverables remain separated by database, auth/membership, product rules, presentation and release boundaries.
